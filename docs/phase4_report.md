# フェーズ4（費用の見積もりと本実行）報告：実行前

本実行の費用は約0.43ドル（為替を1ドル150〜160円とすると70円前後）と見積もった。仕様書の上限1,000円を大きく下回る。課金のある呼び出しは840回で、毎分10回に抑えると約1時間半かかる。本実行はまだ行っていない。

承認してほしいのは次の3点。

1. 本実行（全9条件、各40問×3回）を始めてよいか。
2. APIキーの種類。トライアルキーなら毎分10回・月1,000回までで、今回の840回で月の枠のほとんどを使う。本番キーなら毎分の上限を上げて、30分ほど（APIの呼び出し約10分と、条件EのCPU計算約14分）で終えられる。
3. 指標の扱い（§5）。特に指示がなければ、この案で集計する。

## 1. 疎通確認：v5はトークン課金だった

フェーズ1で予定した1回だけを呼んだ。`rerank-v5.0-fast` に、q01の質問と実際のチャンク3件を渡し、Context Focus（threshold 0.1）を有効にした。生の応答は `results/2026-10-25/smoke/rerank_v5_fast_smoke.json` にある。

| 確かめたこと | 結果 |
| --- | --- |
| 課金単位 | `billed_units` は `input_tokens: 916` だけ。v5はトークン課金で、Context Focusを有効にしても出力トークンは課金されなかった |
| 文字数あたりのトークン数 | 文書3件で992字、質問50字。質問を文書ごとに数えると、1文字あたり約0.80トークン |
| スパンの位置 | `text[start:end]` で、日本語の文の区切りどおりに切り出せた。スパンは関連の高い順に並ぶ |
| スパンが返らない文書 | 関係のない文書（スコア0.003）では `relevant_spans` 自体が返らない（ドキュメントの記述どおり） |
| スコア | 正解の 2505-02 が0.827、部分正解の 2505-01 が0.526、無関係の 2585-02 が0.003 |
| 遅延 | 652ミリ秒 |

関係の薄い見出し行にもスパンが返った（2505-02 の先頭行に0.401）。threshold 0.1 では本文のほぼ全文がスパンとして残るので、トークンがどれだけ減るかは threshold 0.4 のほうで差が出ると考えられる。

## 2. 条件E（ruri-v3-reranker）は残せる

CPU（4スレッド）で、1問あたり候補20件を順位づける時間を8問で測った。中央値は6.99秒、最大は9.03秒だった。40問×3回で約14分かかるが、本実行はAPIの呼び出し間隔の待ち時間に収まる。ただし、CPUで動かした時間とネットワーク越しのAPIの時間は性質が違う。そのため、遅延の比較表ではEを別の扱いにする。

見積もりの前提は次のとおり。

- トークン数は、候補20件の文字数と質問の文字数×20に、疎通確認で求めた0.80トークン/字を掛けた。1回分（40問×候補20件）で約20万トークンになる。

## 4. 実行の仕組み

`uv run python -m rerank_ja_bench.run` で全条件を実行する。`--dry-run` を付けると、上の表と同じ見積もりだけを出してAPIは呼ばない。

- 各リランカーは `src/rerank_ja_bench/rerankers/` の共通インターフェース（`Reranker.rerank()`）で呼ぶ。Nemotron などは、ここにアダプターを1つ足せば加えられる
- 保存済みの候補20件を同じ順で渡す
- 遅延が時間帯に偏らないよう、問題ごとに条件の順番を1つずつずらしながら交互に呼ぶ。全40問を3回繰り返す
- 生の応答は `results/<日付>/raw/<条件>.jsonl` に1回1行で追記する。途中で止まっても、再実行すると保存済みの分は飛ばすので二重に課金しない
- 課金のある呼び出しは毎分の上限（既定10回）と回数の上限（既定900回）で止める。各条件の最初の1回で課金量を表示し、課金単位が想定と違えばその場で止める
- 実行条件（モデルID、パラメータ、ライブラリの版、開始・終了時刻、課金量の合計）は `results/<日付>/run_meta.json` に記録する

## 5. 指標の扱い（特に指示がなければこの案で集計する）

- Recall@5 は「正解のうち上位5件に入った割合」で数える。1つでも入れば1とする Hit@5 も問題ごとに残す
- 条件Aの時点で Recall@5 がほぼ上限（0.97）なので、主に見るのは MRR と nDCG@10。補助として Hit@1（1位が正解の割合）を加える
- q14 は1段目の上位20件に正解がないので、精度の指標から外し、件数だけを記録する
- 遅延は、3回の中央値を問題ごとに取り、その p50・p95 を出す。条件Eは別の扱いにする（§2）

## 6. 承認後の流れ

承認をもらったら本実行を始め、各条件の最初の1回の課金量を確かめて報告する。終わったら、課金量の合計（実測）と見積もりの差を報告する。そのあとフェーズ5（集計）に進む。
