# Cohere Rerank 5 日本語RAG検証 仕様書

Oct 25, 2026 · @Taiga Shiokawa

## 目的と背景

日本語RAGでCohere Rerank 5に乗り換える価値があるかを、30〜50問の小さな評価で確かめる。結果はXの速報とZennの記事にし、企業向け「リランカー乗り換え検証」の型にする。

- 発信：まず比較表1枚をXに出す。反応が良ければ問題数を増やし、Zennの本記事にする。
- 受注：企業から「うちのRAGで同じ比較を」と頼まれたとき、データを差し替えるだけで回せる状態にする。
- 再利用：同じ評価データと仕組みで、後からNemotron 3.5 RerankやQdrant 1.20のハイブリッド検索も比べる。そのため、リランカーや検索方式を差し替えやすい作りにする。

公式発表では、日本語の精度はRerank 5 Proが89.4、Rerank 4 Proが89.3で、ほぼ同じ。そこで精度だけでなく、Context Focusによるトークン削減と、較正スコアのしきい値が乗り換えの理由になるかも確かめる。

## 検証の問い

次の3つに答えを出す。遅延と1問あたりの費用も合わせて記録する。

1. 日本語の検索精度は、Rerank 4 Proから5 Pro／5 Fastに替えると変わるか。リランカーなしと比べて、どれだけ上がるか。
2. Context Focus（`relevant_spans`）を使うと、LLMに渡すトークンをどれだけ減らせるか。そのとき正解箇所を落とさないか。
3. 較正スコアは日本語でも使えるか。公式が示すしきい値（Pro 0.50、Fast 0.45）だけで、関連あり／なしをどこまで分けられるか。

## 比較する条件

リランカー以外の条件はすべて固定し、同じ候補20件を各リランカーに渡して比べる。

| 条件 | モデル・設定 | 位置づけ |
| --- | --- | --- |
| A | リランカーなし（1段目の検索順のまま） | 基準 |
| B | Rerank 4 Pro | 乗り換え前 |
| C | `rerank-v5.0-pro` | 本命 |
| D | `rerank-v5.0-fast` | 安価・高速版 |
| C2・D2 | C・DにContext Focusを追加（threshold 0.1と0.4） | トークン削減の確認 |
| E（任意） | ruri-v3系の日本語リランカー（ローカル実行） | 無料のOSSとの比較 |

Rerank 4 ProのモデルIDは、公式ドキュメントで確かめてから使う。Eは、GPUなしで遅すぎる場合は外してよい。

固定する条件：

- 1段目の検索：日本語の埋め込みモデル1つ（例：ruri-v3系）で上位20件を取り、ファイルに保存して全条件で使い回す。
- チャンク：分け方と長さを1つに決め、全条件で同じものを使う。
- 各リランカーには、同じ20件を同じ順で渡す。

## 評価データ

公開利用できる日本語の業務文書を1種類選び、そこから質問を40問作る。結果を記事に載せるので、再配布や引用ができるライセンスの文書を選ぶ。

コーパスの候補（どれにするかは着手時にユーザーが決める）：

- 官公庁のガイドラインやFAQ（二次利用を認める利用規約のもの）。業務文書らしさが最も高い。
- Wikipedia日本語版の1分野（CC BY-SA）。集めやすいが、業務文書らしさは弱い。
- 既存の日本語ベンチマーク（例：JQaRA）の一部。すぐ始められるが、自分で作った評価データという強みが出ない。

規模は、文書20〜50本、チャンクで数百〜1,000程度を目安にする。

質問の内訳（40問の例）：

| 種類 | 問数 | 狙い |
| --- | --- | --- |
| 素直な事実検索 | 12 | 基本の性能 |
| 言い換え（本文と違う言葉で質問） | 12 | 言葉が一致しないときの強さ |
| 複数箇所にまたがる | 8 | 正解が2チャンク以上ある場合 |
| 答えがコーパスにない | 8 | 較正スコアのしきい値の確認 |

作り方：

1. Claude Codeが、チャンクから質問案と正解チャンクIDの候補を作る。
2. ユーザーが全問を確かめて直す。LLMが作る質問は本文と同じ言葉を使いがちなので、言い換えの問題は特に人の手を入れる。
3. 正解ラベルは正解チャンクIDのリストにする。必要なら関連度を2段階（完全・部分）で付ける。
4. 1段目の上位20件に正解が1つも入らない問題は、リランカーでは救えない。その数を記録し、指標の計算とは分けて扱う。

形式は`data/qa.jsonl`（`id`、`type`、`question`、`relevant_chunk_ids`）とする。

## 測る指標

精度・速さ・費用・トークン削減・しきい値の5つを、問題ごとに記録してから集計する。

| 指標 | 何を見るか | 対象の問題 |
| --- | --- | --- |
| Recall@5 | 上位5件に正解が入るか | 答えありの問題 |
| nDCG@10 | 正解が上位に来ているか | 答えありの問題 |
| MRR | 最初の正解が何位か | 答えありの問題 |
| p50／p95遅延（ms） | rerank呼び出し1回の時間 | 全問 |
| 1問あたり費用（ドル） | 課金されるトークン数×単価 | 全問 |
| トークン削減率 | Context Focusありで、上位5件の本文トークンが何%減るか | 答えありの問題 |
| 正解箇所の保持率 | 削ったあとも正解の文が残っているか | 答えありの問題 |
| しきい値での分離 | 公式しきい値で「関連あり」とした結果の適合率と再現率。答えなしの問題で全候補がしきい値を下回る割合 | 全問 |

測り方の注意：

- 遅延はネットワーク込みになる。同じ回線と時間帯で条件を交互に走らせ、3回ずつ測って中央値を使う。
- トークン数は、APIの応答に課金量が含まれていればそれを使い、なければトークナイザーで数える。どちらを使ったかを記録する。
- 40問では、数ポイントの差は誤差に埋もれやすい。問題ごとの結果も保存し、記事では「差が数ポイント以内なら同等」と扱う。

## 実装方針

Python（uvで管理）で、1コマンドで全条件を再実行できる仕組みにする。リランカーは共通のインターフェースを持つアダプターにし、後からNemotronやQdrantを足せるようにする。

ディレクトリ構成（案）：

```text
rerank-ja-bench/
├── README.md            # 再現手順、実行日、モデルID
├── pyproject.toml
├── .env.example         # COHERE_API_KEY=
├── data/
│   ├── corpus/          # 元の文書と出典・ライセンス
│   ├── chunks.jsonl
│   ├── qa.jsonl
│   └── candidates.jsonl # 1段目の上位20件（固定）
├── src/
│   ├── chunk.py
│   ├── retrieve.py      # 1段目の検索 → candidates.jsonl
│   ├── rerankers/       # base.py, none.py, cohere.py, ruri.py
│   ├── evaluate.py      # 指標の計算
│   └── report.py        # 比較表とグラフ
├── results/
│   └── YYYY-MM-DD/      # 生の応答、問題ごとの結果、summary.csv
└── tests/
```

- APIの生の応答はすべて保存し、指標は保存した応答から計算する。集計をやり直すたびにAPIを呼ばずに済むようにするため。
- 指標の計算は、手で作った小さなデータでテストする。Recall@5やnDCGの計算ミスは、記事の信頼を落とすため。
- 実行のたびに、モデルID、SDKのバージョン、実行日時、パラメータを結果と一緒に記録する。

## 進め方

6つのフェーズで進め、全体で半日〜1日を見込む。各フェーズの終わりでユーザーに報告し、確認をもらってから次へ進む。

1. 準備（30分）：公式ドキュメントでモデルID・パラメータ・料金・上限を確かめ、リポジトリの骨組みを作る。確認：仕様書と食い違う点。
2. 評価データ（1〜2時間、人の確認が中心）：コーパスを決めてチャンクに分け、質問案40問と正解ラベル案を作る。確認：ユーザーが全問を見て直す。
3. 1段目の検索（30分）：上位20件を作って保存し、正解が20件以内に入る割合を出す。確認：割合が低すぎないか（目安は8割以上）。
4. 費用の見積もりと本実行（30分）：全条件のトークン数と費用を先に見積もって報告し、承認を得てから実行する。
5. 集計（30分）：比較表、グラフ、条件による差が大きい問題の例をまとめる。確認：結果の読み方。
6. 発信用の素材（30分）：Xの速報文案と、Zenn記事の構成案と下書きを作る。

## 制約と注意点

- APIキーは環境変数`COHERE_API_KEY`から読み、`.env`は`.gitignore`に入れる。キーをコード、ログ、結果ファイルに書かない。
- 費用：本実行の前に見積もりを出し、合計が1,000円を超えそうならユーザーに確認する。公式ブログの単価ならずっと安く済むはずだが、課金単位を確かめてから見積もる。
- 公開：記事やXへの投稿はしない。下書きまでがこの作業の範囲。GitHubへのpushも、ユーザーの指示があるまでしない。
- 数字の扱い：公式発表の数値と自分の実測値を、表でも本文でもはっきり分ける。
- 範囲外：LLMで回答を生成して品質を測るのは今回はやらない（次の段階で、同じデータに足す）。NemotronとQdrantも今回は扱わない。
- 仕様書と違う事実（モデルID、パラメータ名、料金など）が見つかったら、公式ドキュメントを優先し、変更点を報告する。

## 参考情報と未確認事項

2026-10-25に公式ページを開いて確認した内容：

- モデルIDは`rerank-v5.0-pro`と`rerank-v5.0-fast`。エンドポイントは`https://api.cohere.com/v2/rerank`。
- Context Focusは`relevant_spans`（`mode`、`threshold`、`max_spans`）で有効にする。既定ではオフ。各結果に、文字位置（`start`、`end`）とスコアつきの該当箇所が返る。
- 較正スコアは、0.7ならおよそ7割の確率で役に立つ、という意味づけ。「役に立つ可能性が高い」境目は、Proが0.50、Fastが0.45。
- 単価は100万トークンあたり、Proが0.05ドル、Fastが0.02ドル（公式ブログに記載）。
- コンテキスト長は32kトークン。Rerank 4からは`model`を替えるだけで移行でき、再インデックスは要らない。
- 日本語の公式スコアは、5 Proが89.4、4 Proが89.3、5 Fastが86.8。いずれも提供元の自社評価。

未確認の点：

- Rerank 4 ProのモデルIDと現在の単価
- 1リクエストあたりの文書数の上限と、課金されるトークンの数え方
- ruri-v3系リランカーの正式なモデル名と、手元での速度
