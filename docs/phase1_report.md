# フェーズ1（準備）報告

確認日：2026-10-25。出典はすべて末尾に並べた。

フェーズ2に進む前に、次の3点を決めてほしい。

1. コーパスを3案（§3）から選ぶ。
2. APIキーの種類を決める。トライアルキーは月1,000回までで、本実行（約840回）を1回流すと再実行の余地がほとんど残らない。商用目的にも使えない。本番キーを推奨する。
3. この実行環境に `COHERE_API_KEY` が設定されていない。疎通確認の1回はまだ行っていない（§1.4）。

### 1.3 仕様書どおりだった点

- モデルID `rerank-v5.0-pro`、`rerank-v5.0-fast` と、エンドポイント `https://api.cohere.com/v2/rerank`。
- `relevant_spans` は既定でオフで、`mode`、`threshold`、`max_spans` で指定する。
- コンテキスト長32k。`model` を替えるだけで移行でき、再インデックスは要らない。
- 日本語の公式スコアは5 Pro 89.4、4 Pro 89.3、5 Fast 86.8。指標はブログ上「RCP-nDCG@10」と書かれている。どれもCohere自身の評価。
- 公式ブログの日付は2026-10-21。

### 1.4 疎通確認はまだしていない

この実行環境に `COHERE_API_KEY` が入っていないため、疎通確認の1回は行っていない。キーが入ったら、次の内容で1回だけ呼ぶ予定にしている。

- モデル `rerank-v5.0-fast`、クエリ1件と短い日本語文書3件、`relevant_spans` を有効にする
- 応答をそのまま保存し、`billed_units` の中身（`input_tokens` か `search_units` か、出力トークンがあるか）と、スパンの位置が日本語の文字位置と合うかを確かめる

### 1.5 費用と呼び出し回数の概算

フェーズ4で正式に見積もる。ここでは課金単位の確認のために、桁だけを見ておく。

前提は、40問、候補20件、1チャンク約400字（約400トークンと仮定）、各条件3回ずつ。1回の呼び出しは約8,000トークンになり、1条件あたり120回・約100万トークンになる。

| 条件 | 呼び出し回数 | 課金量 | 概算 |
| --- | --- | --- | --- |
| B：Rerank 4 Pro | 120 | 120検索単位（候補20件、各文書が500トークン未満なら1回1単位） | 0.30ドル（第三者サイトの単価による） |
| C・C2（2種）：5 Pro | 360 | 約300万トークン | 0.15ドル |
| D・D2（2種）：5 Fast | 360 | 約300万トークン | 0.06ドル |
| 合計 | 840 | | 約0.5ドル |

為替を1ドル150〜160円と仮定すると80円前後で、仕様書の上限1,000円を大きく下回る。ただし呼び出し回数は840回で、トライアルキーの月1,000回にほぼ届く。毎分10回の制限では、全条件を流すのに最低84分かかる。

## 2. リポジトリの骨組み

作ったもの：

```text
.
├── README.md            # 概要とセットアップ手順（再現手順はフェーズ5で書く）
├── pyproject.toml       # uv管理。cohere 7.3、sentence-transformers、CPU版torch など
├── uv.lock
├── .env.example         # COHERE_API_KEY=
├── .gitignore           # .env、.venv、キャッシュ、.DS_Store
├── docs/
│   ├── spec.md          # 仕様書（元のファイル名から変更）
│   └── phase1_report.md # この報告
├── data/corpus/
├── src/rerank_ja_bench/
│   └── rerankers/
├── results/
└── tests/
```

仕様書の案から変えた点が4つある。

- 仕様書は `docs/spec.md` という名前で置かれていなかった（元の名前は `docs/Cohere Rerank 5 日本語RAG検証 仕様書.md`）。依頼文に合わせて `docs/spec.md` に名前を変えた。
- `src/` の直下にモジュールを並べるとパッケージとして読み込めないので、`src/rerank_ja_bench/` の下に置く。`chunk.py`、`retrieve.py` などは、使うフェーズで作る。
- ディレクトリ名 `rerank-ja-bench/` はリポジトリ名に合わせてルートに展開し、パッケージ名だけ `rerank_ja_bench` にした。
- Linuxでは、CUDA版のtorch（数GB）を避けてCPU版を入れるようにした。macOSでは通常のPyPI版が入る。

`uv sync` で依存関係を入れ、`cohere`（7.3.0）、`sentence-transformers`（6.2.0）、`torch`（2.14.1+cpu）が読み込めることを確かめた。`.DS_Store` が2つコミットされていたので、追跡から外して `.gitignore` に入れた。

## 3. コーパスの候補

規模の目安は仕様書どおり、文書20〜50本、チャンク数百〜1,000。

| | A. 国税庁タックスアンサー（1分野） | B. Wikipedia日本語版（1分野） | C. JQaRAの一部 |
| --- | --- | --- | --- |
| 出典 | 国税庁ホームページ「タックスアンサー」（nta.go.jp/taxes/shiraberu/taxanswer/） | Wikipedia日本語版。前処理済みの `singletongue/wikipedia-utils`（400字ごとのパッセージ）も使える | Hugging Face `hotchpotch/JQaRA` |
| ライセンス | 公共データ利用規約（第1.0版）。CC BY 4.0と互換で、商用利用・加工・再配布ができる。出典の記載と、加工したことの記載が要る。ロゴやキャラクターは対象外 | CC BY-SA 4.0（またはGFDL）。チャンクをリポジトリで配る場合、そのデータも同じライセンスにする必要がある | 質問・回答はJAQKETのCC BY-SA 4.0、本文はWikipediaのCC BY-SA 4.0 |
| 規模 | 全体で757項目。分野別に所得税208、消費税117、法人税113、譲渡所得71、源泉所得税65、相続税52など。1項目は本文で数千字（医療費控除のページはナビ込みで約4,200字）。1分野から30〜50項目を選ぶと、チャンクは数百になる見込み | 1分野を20〜50記事選ぶ。記事の長さの差が大きいので、チャンク数は選び方で変わる | testは1,667問、各問に候補100件（1件400字以下）。devは1,737問・候補50件。40問を抜き出すと約4,000パッセージ |
| 業務文書らしさ | 高い。「〜のとき」「〜の要件」のような実務のQ&Aで、言い換えの問題（「病院代は戻ってくる？」→医療費控除）を作りやすい | 弱い。百科事典の文体 | 弱い。クイズの質問文 |
| 手間 | 中。HTMLの取得と本文の抜き出しが要る（ページは文字コードが混在しており、Shift_JISのページもある）。質問40問と正解ラベルは自分で作る | 中。質問と正解ラベルは自分で作る | 小。質問と正解ラベルがすでにある |
| 注意点 | 税制改正で内容が変わる。取得日を記録し、取得した版を `data/corpus/` に保存する | 「業務文書での検証」とは言いにくい | 正解ラベルは文字列一致とLLMで付けたもの。ruri-v3-rerankerはJQaRAの結果を公表しており、各社のモデルの学習にJQaRA系のデータが入っている可能性もある。自分で作った評価データという強みも出ない |

同じ条件の官公庁の文書として、個人情報保護委員会の「個人情報保護法ガイドライン」とそのQ&Aもある。こちらもライセンスは公共データ利用規約（第1.0版）だが、配布がPDF中心で取り出しに手間がかかる。また、サイトに「令和８年 改正個人情報保護法」の特集があり、内容が今後改訂される可能性がある。そのため候補からは外した。

提案としてはA案を推す。仕様書が重視する「業務文書らしさ」と「再配布できるライセンス」の両方を満たし、企業の社内FAQに差し替えても同じ形で回せるからだ。分野は、項目数がちょうどよく、内容が実務寄りの源泉所得税（65項目）か、所得税から控除まわりを30〜50項目選ぶかのどちらかが扱いやすいと考える。

## 4. GitHubへのpushについて

仕様書に「GitHubへのpushも、ユーザーの指示があるまでしない」とあるので、変更はローカルにコミットしただけで、pushしていない。この実行環境はセッションが終わると消えるため、残すならpushの指示がほしい（作業ブランチは `claude/happy-galileo-dlit6j`）。
